# 用任务引导提高较弱模型的执行稳定性

`guide` 把需要反复记忆、查找和选择的流程信息交给代码，给模型保留实现方案、业务判断和审查。它不绑定厂商或模型版本，不增加执行门禁，也不代替模型完成代码推理。

## 使用方式

通过 `begin` 或 `start` 创建工作项后，需要引导或恢复上下文时运行：

```powershell
node .ai-harness/bin/harness.mjs guide --id ITER-001 --json
# 多任务时可指定当前负责的任务
node .ai-harness/bin/harness.mjs guide --id ITER-001 --task T1 --json
# 需要相关源码/测试时才加入上下文
node .ai-harness/bin/harness.mjs guide --id ITER-001 --context --json
```

`begin` 的返回值包含 `guide` 命令入口。原有命令继续可用，熟悉任务的模型可以直接推进；不要求每次操作前都调用引导。

输出集中提供：

| 字段 | 用途 |
| --- | --- |
| `workItem` | 恢复目标、验收、非目标和已有授权 |
| `task` / `tasks` | 当前任务、可写范围、验证计划、依赖及所有者 |
| `resources` | 权威输入、适用策略、方案及证据文件位置 |
| `evidence` | 各命令的最新结果，优先显示失败；返工前的结果不充当当前验证 |
| `next.command` | 下一步命令的可执行文件与参数数组，不拼接 shell 字符串 |
| `next.needs` | 必须先查证或完成的判断，包含需要填写的占位符说明 |
| `next.requiresJudgment` | 本步是否需要实际判断；不能照抄占位符直接提交 |
| `next.requiresHumanApproval` / `requiresIndependentReview` | 需要真实批准或独立复核，不能自填通过来解锁 |
| `context`（可选） | 明确实现、声明测试、公开文档及有限本地导入/调用方；附路径、哈希和截断标记 |
| `shortcuts` | 普通已验证迭代的 `finish` 参数建议；仍须填写真实审查、文档和验收结论 |

命令只是建议，不会自动执行，也不会创建证据或改变状态。任务范围、授权和实际结果仍以工作项及原命令校验为准。多个所有者的未完成任务必须显式选择，依赖未完成的任务不会被建议强行解锁。

## 给模型的任务示例

```text
请实现下面的目标，并以给出的验收条件为准。
目标：……
验收：……
不在范围内：……

按仓库规范建立工作项。拿不准下一步或恢复上下文时读取 guide。
从它给出的相关方案、任务范围和证据开始，不需要扫描整个仓库。
先解决 next.needs 中的实际判断，再使用建议命令；成功退出码不能代替业务验收。
```

在实现前，优先明确一个可验证的输入输出样例、一个容易失败的边界、一个必须保持不变的旧行为。缺少上下文时先读取相应实现、直接调用方和已有测试。这样模型处理的是边界明确的局部问题，验证也能针对它容易遗漏的情况。

审查时对照实际差异追问：目标反例是否真的被修复、调用方是否仍兼容、测试是否会在目标错误重新出现时失败。问题要落到输入、代码或命令结果，不用“全面检查”“确认无误”代替证据。

## 失败和上下文恢复

`guide --context` 最多返回8个文件、16000字符，单文件读取上限64 KiB，总读取上限256 KiB，相邻目录最多检查40个候选。它只识别字面本地导入，不展开通配写入范围，不是完整调用图；缺失与截断内容须按路径补读。

多项检查已在计划中明确时，可用 `run --id ITER-001 --task T1 --all --json` 顺序执行。每项仍独立做权限判断并记录证据；遇失败或拒绝即停止，`notRun` 明确列出其余未运行项。不能与 `--check` 或透传命令混用，也不猜测测试目录。

任务仍为 `IN_PROGRESS` 时，修正实现或自测后可以直接重新验证，不必为每次失败重新打开整个工作项。实际需要 `reopen` 时，CLI会返回重置后的任务状态和下一步命令，避免把 `READY` 误当作可直接运行检查。只有普通已验证迭代才有 `finish` 快捷建议，高风险和未验证任务继续保留原门禁。

- 命令失败时，优先查看引导中的错误和原始证据位置；修复根因后重新验证，不用无关成功命令覆盖失败。
- 同一命令按任务和参数只展示最新一次结果。默认最多展示 5 条命令，额外数量由 `omittedCommands` 明示。
- 每段日志预览最多保留约 1200 字符，裁剪时保留开头和末尾并标记 `truncated`。新版 run 在输出较大时保留脱敏全文 artifact 及其哈希，按该路径读取完整错误；旧证据没有全文 artifact 时仍需查看外部日志或缩小诊断。
- 阻塞时返回实际原因与有条件的恢复命令；必须先确认条件已满足，等待时间不算解除证据。
- 引导不会证明某个测试覆盖了全部验收。即使建议登记 verification，仍须核对测试范围；代码变化后需要重新验证。
- 引导会列出当前代码版本缺少的计划检查，并可直接提供 `run --check V1` 参数。最终审查失败会建议 reopen；重新计划后再执行检查，不能复用旧修订或旧尝试的结果。
- 数据或状态不一致时明确失败，不把损坏的记录转换成继续执行的建议。最终仍使用 `check --ci` 验证完整工作项。

## 如何验证模型效果

程序测试只能验证引导是否正确、只读及遵守门禁，不能证明模型能力等同于更强模型。实际对照应使用同一代码基线、任务、工具权限、预算和独立验收测试，分别运行：

1. 较弱模型使用原有命令。
2. 同一个较弱模型使用 guide 和上述局部验收方法。
3. 较强模型作为参考。

选择真实的小 BUG、已有模块迭代和带依赖的跨文件任务，重复运行以减少偶然性。记录独立验收通过率、回归失败、错误工具调用、人工纠正次数、误称完成、耗时和 token 成本；保留失败样例，不只统计成功任务。

只有第 2 组的实测表现改善，才能说这套引导对该模型和任务有效。固定任务程序与使用方法见 [benchmarks](../../benchmarks/README.md)，真实试跑及边界见 [对照报告](../reports/model-comparison.md)。流程辅助不能保证消除推理、知识或上下文能力差异。
