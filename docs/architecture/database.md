# 数据库设计

## 结论

数据库影响：`不适用`。

## 依据

- Harness v1.0 的状态规模小，按项目仓库隔离，不需要跨项目查询或远程并发服务。
- 工作项、任务和证据需要与代码版本一起审查、复制和恢复，仓库内结构化文件比数据库更直接。
- 引入数据库会增加安装、迁移、凭据、备份和离线可用性负担，与“复制后快速使用”的目标冲突。

## 持久化设计

- 当前状态使用 JSON，事件和命令证据使用只追加 JSONL。
- 写入采用同目录临时文件加原子替换，避免进程中断产生半写文件。
- 每条事件包含 schema 版本、工作项、时间、动作和前后状态；时间用于审计，不参与状态路由。
- 任务依赖、状态和门禁由确定性代码校验，不从 Markdown 推断。
- 输出必须脱敏并限制长度；完整敏感日志不进入仓库。

## 未来触发重新评估的条件

只有出现远程多用户控制面、跨仓库全局任务查询、服务端锁/租约或集中审计等明确需求时，才重新评估数据库。届时必须新增 ADR 和迁移方案，不能将 v1.0 文件状态静默替换为数据库。
