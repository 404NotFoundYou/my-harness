# 现有使用场景的优化优先级

证据时点：2026-09-15，本地main/afb485e；本次只读核对产品源码和已有记录，没有重新调用模型或重跑产品测试。

## 判断

PROVEN：上轮复验Luna原流程完整完成3/3，Luna+Harness为1/3；两组功能验收都是3/3。记录支持优先处理任务声明与流程交互成本，不支持宣称模型能力已得到普遍提升。来源：MODEL-BENCHMARK-001/comparison.md。

## 建议顺序

1. 结构化任务输入与创建时诊断（最优先）。PROVEN：cli.mjs的many只收集重复参数；实测把两个路径写成一个逗号串，直到finish才因范围不匹配失败。PROPOSAL：保留现有CLI，新增begin --spec <JSON文件>一类入口，将写入范围、检查命令及参数表示为数组。在现有必填字段和命令语法校验之外，创建前诊断疑似路径列表拼接、无法识别的N/A标记等，并给出纠正方式；不自动拆分合法带逗号文件名，也不自动扩大授权。验收：原误用样例在创建阶段给出可执行纠正信息，正确输入可以完成原流程，旧CLI保持兼容。

2. 一个明确的下一步与可恢复收尾。PROVEN：guide.next在普通任务通过检查后仍逐项建议record/状态转换，finish放在另一个shortcuts列表；compact.finish只允许IMPLEMENTING+IN_PROGRESS，执行中断后需手动恢复细粒度步骤。PROPOSAL：符合精简条件时把finish作为主要建议；收尾能从合法中间状态继续，并在已有真实证据、代码版本与授权仍有效时复用结果。验收：中断后一次恢复入口即可完成剩余步骤，不重复已通过检查，不伪造审查或验收，不绕过高风险独立复核。

3. 减少默认上下文与重复读取。PROVEN：策略索引对ITERATION无条件包含database.md，实测还有guide --context后再读取相同源码的现象。PROPOSAL：保留数据库影响判断，按已记录影响决定何时加载完整专项规则；支持客户端传入已读文件指纹，仅返回变化内容或摘要，保持guide只读。验收：无数据库影响任务不加载完整数据库设计细则，相关任务仍加载；重复请求可定位变化且显式标记省略，不把未读内容算作已检查。尚未证明这会带来多少时延收益。

4. 补齐现有三客户端的实际验证与耗时拆分。PROVEN：benchmark入口固定调用codexDriver；驱动记录整体耗时，未形成完整的逐工具时序。PROPOSAL：在现有Gemini/Claude/Codex范围内补兼容验证，记录规则加载、工具执行、恢复和验收行为；区分工具执行时间与模型/网络等待，加入少量真实仓库修改并重复采样。验收：能指出流程成本发生在哪一步；不把模型/网络等待直接叫作纯推理耗时，不以单次结果宣称通用提升。

优先实施前两项，再衡量收益决定是否继续第三项。暂不建议增加更多角色、多Agent层次或通用强制检查点。收益目标是降低无效调用、参数错误和中间状态操作，而非降低验证要求。

## 边界

以上均为建议，尚未实现。单任务效果提升比例、Gemini/Claude真实兼容性及各环节耗时仍未验证。当前无分析阻塞或延期；仅生成分析控制面记录。实际执行了doctor和policies，本项完成后以check --ci核对工作项完整性，该命令不等于重新运行产品测试。
