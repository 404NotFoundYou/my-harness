# BUG 修复策略

## 定位

- 复现优先：记录实际/期望行为、环境、版本、输入、触发条件和日志/堆栈。无法复现且证据不足时不得猜测修改。
- 阅读目标代码、调用方、配置、数据/API 契约和测试，确定影响与明确不影响范围。
- 用失败测试、最小复现、日志、调试或二分证实根因；相关性和“改后不报错”不是根因证据。
- 修改前优先建立失败测试；无法建立时记录原因和等价证据。

## 修复

- 只改根因和直接关联代码，不扩功能、不重构、不改变未批准契约。
- 禁止硬编码样例、扩大重试、吞异常、跳过断言、禁用测试或无条件成功来掩盖问题。
- 必须改变产品行为、数据口径、API、权限或支持范围时，停止并转为 `ITERATION`。

## 验证与审查

- 修复后用同一复现路径确认恢复预期，再验证调用方、边界、平台和已有测试。
- 每次 BUG 修改或 Review 返工后必须重新运行受影响验证并立即 Code Review；批次大小固定为 1。
- 记录根因、修复、影响、命令结果、审查、未验证项和文档影响；无文档影响写 `N/A: 理由`。
