# 核心开发策略

## 先思后码

- 明确前提、未知项、范围和成功条件；影响业务行为的歧义必须询问。
- 阅读目标文件相关完整部分、导出接口、直接调用方、公共工具和测试后再修改。
- 发现更简单方案必须提出；禁止需求外功能、猜测性抽象和顺手重构。
- 当前仓库规范优先于 AI 偏好；实质冲突必须暴露并选择权威来源。

## 工作规模

- 在运行任何 Runtime 命令前只做一次规模判定，并选择一条执行路径。
- `TRIVIAL_READONLY`：可通过直接读取或少量无副作用确定性命令回答的单一事实；直接检查并简洁报告，不运行 Runtime 命令、不创建工作项或检查点。
- `TRIVIAL_EDIT`：不改变业务行为、API、Schema、依赖、配置、安全或发布的单文件机械修改；读取目标上下文后直接修改，只运行一个与改动直接相关的最窄验证并报告，不运行 Runtime 命令或仓库级 `check --ci`。
- `NON_TRIVIAL`：业务行为、多文件/模块、数据库、API、依赖、配置、安全、UI 页面、跨端、迁移、发布、外部副作用或需要持续调查/方案裁量的工作；必须由 Runtime 工作项跟踪。
- 所有 BUG 使用 `BUGFIX`；简单 BUG 只允许轻量计划，不能跳过复现、验证和 Code Review。
- 分类不确定时选择 `NON_TRIVIAL`。禁止拆分任务规避门禁；轻量任务在写入前发现越界时停止并升级为工作项。

## 执行

- 技术/领域设计先明确业务流程、接口及查询写入草案；数据库决策完成后才建立任务执行计划。
- 计划批准后连续执行所有可执行任务，不逐任务询问；阻塞任务记录证据，继续其他独立任务。
- 每个任务只在计划写入范围内修改，并同步其文档影响或记录 `N/A: 理由`。
- 确定性转换、依赖解锁、哈希、路由和重试由 runtime 或常规代码处理，不能让模型凭感觉维护。
- 每个重要任务完成后运行最窄验证，记录原始结果，再进入任务/批次 Code Review。
- 测试必须表达所保护的业务原因；若破坏业务规则后测试仍通过，测试设计无效。

## 失败与声明

- 跳过、失败、超时、环境缺失和未运行项必须明确为 `未验证`，不得宣称通过。
- `IMPLEMENTED` 不是 `COMPLETED`；任务验证和 Code Review 均通过后才能完成。
- 代码完成、构建通过、PR 创建或 AI 自评都不等于 `DONE`。
- 轻量任务不使用 `DONE`/`ANSWERED` 状态词，只报告请求结果和实际最窄验证；不得将局部验证表述为全量测试通过。
- 最终输出区分已实现并验证、已实现未验证、未实现、阻塞/延期、实际命令和交付物。
