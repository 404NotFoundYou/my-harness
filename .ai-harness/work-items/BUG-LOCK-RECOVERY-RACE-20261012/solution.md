# 并发旧锁恢复修复方案

2026-10-12 的 Windows 22 CI 在同一进程内并发调用两次 `recoverLock` 时，两方分别在释放和移动锁目录阶段得到 `ENOENT`，未产生预期的一次成功。日志证明原测试的竞态失败，不证明底层 `rename` 的具体时序；本项不把重跑成功当作修复证据。

当前 `recoverLock` 先异步检查失活所有者，再各自重命名所有者文件为不同认领文件，最后调用恢复动作和释放目录。对本次同进程路径，在第一次异步操作之前同步取得磁盘上现存锁目录的 `realpathSync.native`（Windows 忽略大小写）作为占用键；同进程竞争者返回明确的 `LOCK_CHANGED`，不触碰文件、不执行恢复动作。目录已不存在时保留原有 inspectLock 的失败判断，不把不存在路径当作可恢复锁。`finally` 释放本进程占用，无论旧锁校验、动作或清理是否失败。跨进程仍由原有文件认领路径处理；不改磁盘格式、旧认领中断恢复或外部权限策略。

验证先在测试中受控安排两个请求均观察旧所有者，再模拟 Windows 日志体现的双重认领返回，断言恢复动作最多一次、恰一方完成；该测试应在旧实现上失败。独立审查指出词法路径键无法识别 Windows `\\?\` 命名空间别名；将第二个调用改为该别名后再次获得 2 次动作的失败复现，物理路径键修正后转绿。修复后执行同一复现、锁/工作项恢复与 benchmark 续跑回归，以及适用的静态和隔离执行检查。跨进程竞争及真实 Windows 时序由 CI 与独立复核再次评估；若证据表明同进程保护不足，应返工而不是降低断言或宣称通用竞态已解决。

无数据库影响：仅运行时临时锁的同进程调度，不改变 Schema、业务持久化数据或查询。高风险：锁恢复影响并发互斥及故障恢复，必须独立审查，不能将本机测试通过等同于跨进程安全。
